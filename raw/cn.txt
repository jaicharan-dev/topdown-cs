User prompt: Q2 [Easy]: What's the fundamental difference between TCP and UDP? Give one real-world example where UDP is deliberately chosen over TCP, and explain why reliability is sacrificed in that case.
Response: The fundamental difference comes down to a tradeoff: TCP prioritizes perfect reliability and order, while UDP prioritizes raw speed and lower overhead.
TCP (Transmission Control Protocol) is connection-oriented. Before sending a single byte of actual data, it performs a "three-way handshake" to establish a secure connection. If a packet gets lost along the way, TCP automatically stops, requests a retransmission, and ensures everything is perfectly reassembled in the correct sequence.
UDP (User Datagram Protocol) is connectionless. It simply fires packets at the destination address without checking if they arrive, in what order they arrive, or if the receiver is even listening.
Real-World Example: High-Frequency Trading (HFT)
In fintech, High-Frequency Trading firms deliberately use UDP for live market data feeds (like stock price ticks broadcasted by the exchange).
They sacrifice reliability for speed because late data is worse than lost data. If a price tick is dropped using TCP, the protocol will halt the stream, request a retransmission, and wait for it to arrive. By the time that dropped packet is successfully delivered milliseconds later, the stock price has already changed again—the data is stale and entirely useless for an algorithm making split-second decisions.
With UDP, if a packet drops, the system simply ignores it and instantly processes the next incoming tick.
The Interview Answer (30-45 seconds)
"The core difference is that TCP is connection-oriented and highly reliable, while UDP is connectionless and built for speed. TCP uses a three-way handshake to establish a connection, guarantees data delivery, checks for errors, and ensures packets are processed in the correct order. UDP skips all of that overhead—it just fires packets at the destination without waiting for acknowledgments.
Because of this, UDP is deliberately chosen when speed is more critical than perfect data integrity. For example, in fintech, stock exchanges broadcast live market data feeds using UDP. If a packet gets dropped, a high-frequency trading algorithm doesn't want the network to pause and wait for a retransmission—that data is already stale. It's much better to lose that packet entirely and immediately process the next real-time price update."

User prompt: Q3 [Medium]: Walk through the TCP 3-way handshake — what's exchanged at each step, and why does establishing a connection need 3 steps instead of 2? Then explain why terminating a TCP connection takes 4 steps instead of 3, and what a "half-closed" connection means in that context.
Response: The TCP 3-way handshake is how a client and server establish a reliable connection before exchanging any data. It ensures both sides are ready to speak and agree on sequence numbers to track the data.
The 3-Way Handshake
SYN (Synchronize): The client sends a packet with the SYN flag set to the server, along with a random initial sequence number (e.g., 100). This means, "I want to connect, and my data will start at sequence 100."
SYN-ACK (Synchronize-Acknowledge): The server receives this and replies with a packet that has both SYN and ACK flags set. It acknowledges the client's sequence (ACK 101) and sends its own random sequence number (e.g., 500). This means, "I hear you. I'm ready to receive your data, and my own data will start at sequence 500."
ACK (Acknowledge): The client receives the SYN-ACK and sends back an ACK (ACK 501) to acknowledge the server's sequence number.
Why 3 steps and not 2? A 2-way handshake (SYN, SYN-ACK) would leave a major vulnerability. The server would allocate resources and open a connection as soon as it sends the SYN-ACK, without knowing if the client actually received it. If the client died, or if a malicious user flooded the server with fake SYN packets (a SYN Flood attack), the server would keep hundreds of connections open waiting for clients that aren't there, eventually crashing. The 3rd step proves the client is real and actively listening.
Terminating the Connection (4-Way Handshake)
TCP is a full-duplex protocol, meaning data flows in two independent directions simultaneously (Client to Server, and Server to Client). Because these two streams are independent, they must be shut down independently.
Why 4 steps instead of 3? When the client says "I'm done talking" (sends a FIN packet), the server acknowledges it (sends an ACK). The client's outgoing stream is now closed.
However, the server might still have half a megabyte of data it was in the middle of sending to the client. If termination was only 3 steps, the server would have to instantly kill its own transmission. Instead, the server keeps its outgoing stream open, finishes sending its remaining data, and only then sends its own FIN packet. The client acknowledges this final FIN, fully closing the connection.
This temporary state where one side has closed its transmission but can still receive data from the other side is called a half-closed connection.
The Interview Answer (60 seconds)
"To establish a TCP connection, we use a 3-way handshake: SYN, SYN-ACK, and ACK. The client requests a connection (SYN), the server acknowledges it and opens its own side (SYN-ACK), and the client acknowledges the server's response (ACK). It requires three steps because TCP is bidirectional—both sides must prove they are alive and can receive data before resources are fully committed, which also prevents stale connections from exhausting server memory.
Terminating a connection, however, takes a 4-way handshake. Because TCP is full-duplex, the two directions of data flow are independent and must be closed independently. If a client sends a FIN to close its transmission, the server immediately ACKs it. But the server might still have data buffered to send back. It enters a 'half-closed' state—the client can no longer send, but it can still receive. Once the server finishes transmitting its remaining data, it sends its own FIN, which the client ACKs, completing the 4 steps and fully closing the connection."

User prompt: Q4 [Medium]: Flow control and congestion control are often confused, but they solve two different problems. Define both, explain what each is protecting against, and name at least one algorithm associated with congestion control (e.g. Slow Start, AIMD).
Response: Think of sending data over a network like managing cars in a physical traffic system.
Flow control is about the destination's parking garage. Congestion control is about the highway itself.
Flow Control: Protecting the Receiver
Flow control guarantees that a fast sender does not overwhelm a slow receiver.
Imagine a powerful server sending a large file to an old 3G smartphone. If the server blasts data at 1 Gigabit per second, the phone's internal memory buffer will instantly fill up, and it will drop all subsequent packets.
TCP solves this using a Sliding Window mechanism. The receiver constantly advertises its "Receive Window" (rwnd) back to the sender. This number essentially says, "I currently have exactly 50KB of free buffer space." The sender is strictly forbidden from sending more than 50KB of unacknowledged data. If the receiver's buffer fills entirely, it advertises a window size of 0, forcing the sender to halt until space clears up.
Congestion Control: Protecting the Network
Even if the destination parking garage is entirely empty (the receiver has a massive buffer), if 10,000 cars enter the highway at the exact same millisecond, you get a massive traffic jam at the toll booths (routers).
Congestion control protects the network path itself. It prevents too many senders from overwhelming the intermediate routers, which causes queue overflows and widespread packet loss. Because routers do not explicitly tell senders their capacity, TCP has to guess the network's speed and adjust dynamically.
A core algorithm for this is AIMD (Additive Increase, Multiplicative Decrease) combined with Slow Start:
Slow Start: The sender starts with a tiny Congestion Window (cwnd), usually 1 or 2 segments. If those arrive successfully, it doubles the window. It keeps doubling exponentially to quickly find the network's capacity.
Congestion Avoidance (Additive Increase): Once it hits a certain threshold, it switches to linear growth, adding just 1 segment per round trip to cautiously probe the upper limit.
Multiplicative Decrease: The moment a packet drops (usually detected by 3 duplicate ACKs or a timeout), TCP assumes the network is congested. It immediately cuts its sending rate in half (or drops back to 1) to relieve the traffic jam, then slowly builds back up.
The Interview Answer (60 seconds)
"Flow control and congestion control solve two different bottlenecks in a network connection.
Flow control protects the receiver. It prevents a fast sender from overwhelming a slower receiver's memory buffer. TCP handles this using the Sliding Window protocol. The receiver continuously advertises its available buffer space (rwnd) to the sender, and the sender is strictly capped by that number.
Congestion control, on the other hand, protects the network path. Even if the receiver can handle high speeds, the intermediate routers might be overwhelmed by too much traffic from multiple sources. Because routers don't explicitly advertise their capacity, TCP senders have to deduce it. They use algorithms like Slow Start—where the sender starts transmitting very slowly and exponentially increases its rate until it hits a threshold—and AIMD (Additive Increase, Multiplicative Decrease), where the sender linearly increases its transmission rate to probe for capacity, but instantly cuts its rate in half the moment a packet is lost, thereby relieving the network congestion."

User prompt: next question Q5 [Easy]: What's the difference between a public and a private IP address? Why do devices with private IPs need NAT to access the internet, and what specific IPv4 problem did NAT help solve at scale?
Response: Think of a Public IP as a company's main phone number listed in a global directory. Anyone in the world can dial it. A Private IP is like an internal desk extension (e.g., Ext. 104) inside that company's building. It only works if you are already inside the building.
Public IP addresses are globally unique and routable on the internet. They are assigned by your Internet Service Provider (ISP).
Private IP addresses (like 192.168.x.x or 10.x.x.x) are locally unique to your specific Local Area Network (LAN). They are not routable on the public internet.
Because private IPs are only valid locally, millions of homes around the world can reuse the exact same private IP (192.168.1.5) for their laptop without causing any conflicts.
Why NAT is Needed
Because private IPs aren't valid on the public internet, a device like 192.168.1.5 cannot request a webpage from Google directly. Google's servers wouldn't know how to send the data back, because there are millions of devices claiming to be 192.168.1.5 globally.
Network Address Translation (NAT) acts as the receptionist. When your laptop sends a request to the internet, your home router intercepts it. The router strips off your private IP and replaces it with the router's one Public IP. It keeps a mapping table (using port numbers) so that when Google replies to the router's public IP, the router knows exactly which internal device requested the data and forwards it to the correct private IP.
The IPv4 Problem Solved
NAT solved the IPv4 Address Exhaustion crisis. The IPv4 protocol only has about 4.3 billion possible addresses. With the explosion of the internet, we ran out of public IPs very quickly. By using NAT, an entire university campus or corporate office with 10,000 devices only needs one (or a small handful) of public IP addresses. All 10,000 devices use private, reusable IPs internally, and NAT multiplexes them out to the internet. This drastically slowed down the depletion of the global IPv4 pool while the world slowly transitions to IPv6.
The Interview Answer (45 seconds)
"A public IP address is globally unique and routable on the public internet, whereas a private IP address is only valid locally within a specific network. Because private IPs are non-routable, multiple homes or businesses can reuse the exact same private addresses, like 192.168.1.1, without conflict.
However, this means a device with a private IP cannot talk to the internet directly. It requires NAT—Network Address Translation. When an internal device sends traffic out, the router swaps the device's private IP with the router's own public IP, and keeps a record of this translation using port numbers. When the response comes back, the router forwards it to the correct internal device.
NAT was crucial for solving the IPv4 exhaustion problem. Because IPv4 only has roughly 4.3 billion addresses, NAT allowed entire organizations with thousands of internal devices to share just a single public IP address, massively conserving the global IP pool."

User prompt: Q6 [Medium]: Walk through what happens when a browser needs to resolve a domain name to an IP address — what's the order of caches checked before a full lookup is triggered, and what happens during the recursive DNS lookup itself (root → TLD → authoritative)? Bonus: what's the difference between a recursive and an iterative DNS query?
Response: To resolve a domain name like example.com into an IP address, your system first checks a hierarchy of local caches. If the IP address isn't found locally, it triggers a full lookup across the internet.
1. The Cache Hierarchy
Before asking the internet, your computer checks its memory in this specific order to save time:
Browser Cache: The web browser itself caches DNS records for a set time (TTL).
OS Cache: If the browser doesn't have it, the operating system checks its own DNS client cache and the local hosts file.
Router Cache: If the OS fails, the request is sent to your local network router, which maintains its own cache.
ISP Cache (Recursive Resolver): Finally, the request leaves your home network and hits the DNS resolver provided by your Internet Service Provider (or a public one like Google's 8.8.8.8). If the resolver has the IP cached, it returns it.
If all four caches miss, the recursive resolver must perform a full DNS lookup.
2. The Full Lookup (Root → TLD → Authoritative)
Think of the full lookup as asking a librarian to find a specific book by narrowing down the sections of a massive library.
Root Nameserver: The recursive resolver asks one of the 13 logical root servers worldwide, "Where is example.com?" The root server doesn't know the exact IP, but it reads the .com extension and replies, "I don't know, but here is the IP for the .com Top-Level Domain (TLD) server".
TLD Nameserver: The resolver then asks the .com TLD server. The TLD server manages all .com domains. It replies, "I don't have the final IP, but I know example.com is managed by this specific Authoritative Nameserver".
Authoritative Nameserver: Finally, the resolver asks the authoritative nameserver for example.com. This server holds the actual DNS records (like the 'A Record') and replies, "The exact IP address for example.com is 192.0.2.1".
The recursive resolver caches this answer for future requests and hands it back to your browser.
Bonus: Recursive vs. Iterative Queries
Recursive Query: A request demanding a complete answer. When your browser asks the ISP resolver, it is saying, "Find me the final IP address, or return an error. I will not do any extra work."
Iterative Query: A request accepting partial answers. When the resolver talks to the Root and TLD servers, it is saying, "If you don't know the exact IP, just give me a referral to the next best server to ask."
The Interview Answer (60 seconds)
"When resolving a domain, a system checks local caches first to save time. It checks the browser cache, the operating system cache, the local router cache, and finally the ISP's recursive resolver cache.
If the IP isn't cached anywhere, the recursive resolver performs a full lookup. It first queries a Root Nameserver, which directs it to the appropriate TLD Nameserver based on the domain extension, like dot-com. The resolver then asks the TLD server, which points it to the Authoritative Nameserver for that specific domain. The authoritative server holds the actual DNS records and returns the final IP address to the resolver, which passes it back to the client.
As a bonus: the difference between recursive and iterative queries lies in the expectation. The client makes a recursive query to the resolver, demanding the final IP address. The resolver, however, makes iterative queries to the Root and TLD servers, meaning it accepts partial answers or referrals to other servers until it finds the final authority."

User prompt: Q7 [Easy]: What are the main components of an HTTP request? Then explain what HTTPS adds on top of HTTP, and name at least 3 common HTTP status codes with what each signifies.
Response: An HTTP request is how a client (like your web browser) asks a server for data. It is sent entirely in plain text.
The 3 Main Components of an HTTP Request
The Request Line: This is the core command. It contains:
The Method (e.g., GET to read data, POST to send data, PUT to update, DELETE to remove).
The URI/Path (e.g., /images/logo.png).
The HTTP Version (e.g., HTTP/1.1 or HTTP/2).
The Headers: These are key-value pairs that act as metadata. They tell the server who is asking and what format they expect. Examples include Host: [www.example.com](https://www.example.com), User-Agent: Mozilla/5.0, and Accept: text/html.
The Body (Optional): This contains the actual payload being sent to the server. A GET request usually has no body, but a POST request (like submitting a login form or uploading a file) will include the data here.
What HTTPS Adds (The "S" is for Secure)
HTTP sends all of its components (including passwords in the Body and session cookies in the Headers) in plain text. Anyone intercepting the network traffic can read it perfectly.
HTTPS (Hypertext Transfer Protocol Secure) is simply HTTP layered inside a secure TLS (Transport Layer Security) tunnel. Before sending the HTTP request, the client and server perform a TLS Handshake.
HTTPS adds three critical guarantees:
Encryption: It scrambles the plain text into unreadable ciphertext. Even if intercepted, the data is useless without the decryption key.
Authentication: It verifies the server's identity using digital certificates issued by a Certificate Authority (CA), proving you are actually talking to your bank, not an imposter.
Data Integrity: It ensures the data wasn't tampered with in transit.
3 Common HTTP Status Codes
When the server replies, it includes a 3-digit status code.
200 OK: Success. The request was received, understood, and processed successfully.
404 Not Found: A Client Error. The client successfully communicated with the server, but requested a resource (like a specific URL path) that doesn't exist.
500 Internal Server Error: A Server Error. The client's request was valid, but something crashed or went wrong on the server's backend while trying to fulfill it.
The Interview Answer (45-60 seconds)
"An HTTP request consists of three main parts. First is the Request Line, which includes the HTTP method like GET or POST, the path, and the protocol version. Second are the Headers, which provide metadata like the Host or User-Agent. Third is the optional Body, which contains payload data for methods like POST or PUT.
The problem with standard HTTP is that all this data is sent in plain text. HTTPS adds a TLS encryption layer over it. Before sending the HTTP data, the client and server perform a TLS handshake to establish a secure tunnel. This adds encryption to keep data private, authentication via digital certificates to prove the server's identity, and integrity checks to ensure the data wasn't altered.
When the server responds, it uses status codes. Three common ones are 200 OK, meaning the request succeeded; 404 Not Found, a client error meaning the requested resource doesn't exist; and 500 Internal Server Error, meaning the request was valid but the backend server crashed while processing it."

User prompt: Q8 [Medium]: Compare cookie-based session authentication with token-based authentication (JWT). Specifically: where is the authentication state stored in each approach, and what's the key tradeoff (in terms of scalability vs. control/revocation) that pushes a system toward one over the other?
Response: The core difference between session-based and token-based authentication comes down to where the state is stored.
Cookie-Based Session (Stateful)
In a session-based approach, the authentication state is stored on the server (e.g., in memory, a database, or a Redis cache). When a user logs in, the server creates a session record and sends a short, random session_id string back to the client, usually set as an HttpOnly cookie. On subsequent requests, the browser automatically sends this cookie. The server reads the session_id, looks it up in its database, and if a matching active session exists, the user is authenticated.
Token-Based JWT (Stateless)
In a JWT approach, the authentication state is stored entirely on the client. When a user logs in, the server packages the user's data (claims, roles, expiration) into a JSON object, signs it cryptographically using a secret key, and sends this JSON Web Token (JWT) to the client. The server does not save this token anywhere. On subsequent requests, the client sends the JWT (usually in the Authorization: Bearer header). The server simply verifies the cryptographic signature. If the signature matches and the token hasn't expired, the user is authenticated.
The Key Tradeoff: Scalability vs. Control
This architectural split forces a major tradeoff between horizontal scalability and absolute control over revocation.

When to choose which:
Choose JWT if you are building a highly distributed microservices architecture where hitting a central Redis database for every single API call would create a massive bottleneck.
Choose Sessions if you need strict, instantaneous control over user sessions (e.g., banking, streaming services enforcing screen limits, or enterprise apps where an admin must instantly revoke a compromised employee's access). To mimic this control with JWTs, you have to maintain a "blacklist" of revoked tokens on the server, which defeats the entire purpose of being stateless.
The Interview Answer (60 seconds)
"The fundamental difference is where the authentication state lives. Cookie-based sessions are stateful: the server stores the active session in a database or cache, and the client just holds a random session_id to reference it. JWTs are stateless: the server cryptographically signs a payload containing the user's data and hands it to the client. The server doesn't remember the token; it just verifies the math on the signature when the client sends it back.
The main tradeoff deciding between them is scalability versus control.
JWTs win on scalability because any microservice with the secret key can validate the token independently, eliminating the need to query a central session database on every request. However, sessions win on control and revocation. With a session, if an admin needs to instantly kick a user out, they just delete the session from the database. With a JWT, because the server isn't tracking it, the token remains valid until its expiration timestamp. You'd have to build a server-side blacklist to revoke it early, which defeats the point of being stateless."

User prompt: Q9 [Medium]: Explain the difference between a forward proxy, a reverse proxy, and a load balancer. How does a CDN fit into this picture, and what's a scenario where you'd deploy all three together to scale a web application?
Response: These three components act as middlemen in network traffic, but they serve entirely different purposes and protect different sides of the connection.
1. Forward Proxy (Protects the Client)
A forward proxy sits in front of one or more clients. When a client wants to access the internet, it sends the request to the forward proxy first. The proxy forwards the request to the destination server, receives the response, and sends it back to the client.
The key trait: The destination server does not know which client actually made the request. It only sees the proxy's IP.
Use case: Bypassing geographic restrictions (like a VPN), corporate content filtering (blocking employees from social media), or client anonymity.
2. Reverse Proxy (Protects the Server)
A reverse proxy sits in front of one or more servers. When a client from the internet tries to access a website, the request hits the reverse proxy first. The proxy decides which backend server should handle the request, fetches the data, and returns it to the client.
The key trait: The client does not know which backend server actually served the request. It thinks the reverse proxy is the only server.
Use case: Hiding the backend infrastructure's IP, terminating SSL/TLS encryption (so backend servers don't have to waste CPU on it), and caching static content.
3. Load Balancer (A Specialized Reverse Proxy)
A load balancer is a specific type of reverse proxy designed to distribute incoming traffic across a pool of multiple servers.
The key trait: It ensures no single server gets overwhelmed, improving both performance and availability. If one server crashes, the load balancer detects it (via health checks) and instantly reroutes traffic to the healthy servers.
Algorithms used: Round Robin, Least Connections, IP Hashing.
How a CDN Fits In
A CDN (Content Delivery Network) is essentially a globally distributed network of highly optimized reverse proxies. Instead of sending every request to your main data center in New York, a CDN caches static assets (images, CSS, JavaScript) on servers all over the world. If a user in Tokyo requests your site, the CDN's Tokyo "Edge Node" intercepts the request and serves the images instantly, drastically reducing latency.
The Unified Scenario: Scaling a Global Web App
Imagine you are building a global streaming platform like Netflix. Here is how you deploy all three (plus a CDN) together:
A user in London opens your app. The DNS routes their request to the nearest CDN node in London. The CDN instantly serves all the static UI images, JavaScript, and CSS.
The user clicks "Play." This is a dynamic API request, so the CDN forwards it across the ocean to your main data center.
The request hits your Load Balancer. The load balancer sees you have 50 backend servers available and routes the request to Server #12, which currently has the fewest active connections.
Server #12 is actually a Reverse Proxy (like Nginx). It terminates the SSL connection, authenticates the user's JWT token, and routes the internal traffic to the specific "Video Streaming Microservice."
Meanwhile, the video streaming microservice needs to fetch subtitles from a third-party vendor's API. Because your internal servers aren't allowed to access the public internet directly for security reasons, the microservice routes its outbound request through a Forward Proxy, which retrieves the subtitles anonymously and safely.
The Interview Answer (60 seconds)
"A forward proxy sits in front of the client, intercepting outbound requests to the internet. It protects the client's identity and can enforce corporate filtering. The destination server doesn't know who the real client is.
A reverse proxy sits in front of the server, intercepting inbound requests from the internet. It protects the server by hiding its IP, handling SSL termination, and caching. The client doesn't know which backend server actually responded.
A load balancer is essentially a reverse proxy designed specifically to distribute traffic across a pool of servers to ensure high availability and prevent any single server from crashing under load.
To scale a global web app, you would deploy a CDN at the edge to serve static assets locally to the user. Dynamic requests would pass through the CDN to your data center's Load Balancer, which distributes the traffic evenly. Those requests then hit a Reverse Proxy, which decrypts the SSL and routes the traffic to the correct backend microservice. If those backend servers need to securely call external third-party APIs, they might route their outbound traffic through an internal Forward Proxy."

User prompt: Q10 [Medium]: Compare HTTP polling, long polling, and WebSockets for building a real-time feature. What overhead does each approach carry, and what's the key architectural tradeoff you accept when you adopt WebSockets at scale (hint: think about statelessness)?
Response: Building real-time features—whether it's a live stock ticker for a fintech trading platform or instant billing alerts for a subscription tracker—forces a decision on how the client and server communicate.
Here is how the three main approaches handle the problem:
1. HTTP Polling (Regular Polling)
The client repeatedly asks the server, "Do you have any new data?" at fixed intervals (e.g., every 5 seconds). If the server has no new data, it responds with an empty payload.
The Overhead: Massive. Every single request requires a full HTTP header exchange, TCP overhead, and CPU cycles on your backend (like an Express.js server) just to repeatedly say, "No update." It's incredibly inefficient for both bandwidth and battery life.
Best for: Things that change predictably and slowly, where real-time accuracy isn't critical.
2. HTTP Long Polling
The client asks the server for new data, but instead of replying "No" immediately, the server holds the request open until new data is actually available (or a timeout is reached). Once the server responds, the client immediately sends a new long-polling request.
The Overhead: Memory and connection limits. The server is forced to hold hundreds of thousands of HTTP connections open simultaneously while they idle, which can quickly exhaust the thread pool or memory of your backend instances.
Best for: Occasional, asynchronous events (like waiting for a background report to finish generating) where you don't want the overhead of setting up a WebSocket.
3. WebSockets
WebSockets abandon the HTTP request-response cycle entirely. After an initial HTTP handshake, the connection is "upgraded" to a persistent, full-duplex TCP connection. Both the client and the server can push data to each other instantly, at any time, without waiting to be asked.
The Overhead: Minimal per-message overhead. Because the connection stays open, you don't send heavy HTTP headers with every message—just the raw data frames (a few bytes).
Best for: High-frequency, bidirectional data streams (like live fintech order books, multiplayer games, or live chat).
The Architectural Tradeoff at Scale: Stateful vs. Stateless
Standard HTTP is stateless. If you have a load balancer sitting in front of five Node.js backend servers, it doesn't matter which server handles a user's request. Any server can process it and forget about it. You can scale horizontally just by spinning up more instances.
WebSockets are stateful. When a user connects via WebSocket, they form a persistent, dedicated pipe to one specific backend server (e.g., Server A).
If a background worker process finishes updating a database and needs to broadcast an alert to that user, but the worker notifies Server B, the message gets dropped. Server B has no idea who that user is because their active WebSocket connection lives exclusively on Server A.
To scale WebSockets, you accept the tradeoff of managing this state. You typically have to introduce a Pub/Sub Message Broker (like Redis) behind your backend servers. When Server B needs to broadcast a message, it publishes it to Redis. Redis then pushes that message to all backend servers, and Server A finally pushes it down the dedicated WebSocket to the user.
The Interview Answer (60-90 seconds)
"To build a real-time feature, you generally choose between HTTP polling, long polling, or WebSockets.
Standard HTTP polling has the client repeatedly ask the server for updates at set intervals. It carries massive overhead because you're constantly establishing connections and sending heavy HTTP headers even when there's no new data. Long polling improves this by having the server hold the request open until data is ready, but this carries high memory overhead because the server must maintain thousands of idle, hanging connections.
WebSockets are usually the best solution for true real-time needs. They upgrade the connection to a persistent, full-duplex TCP pipe, allowing the server to push data instantly with virtually zero per-message overhead.
However, the key architectural tradeoff when adopting WebSockets at scale is statelessness. Standard HTTP is stateless, making it trivial to load-balance across multiple backend instances. WebSockets are stateful—a user is tethered to one specific server memory space. To scale WebSockets horizontally, you have to introduce a pub/sub layer like Redis so your backend servers can communicate with each other and route messages to the specific server holding the user's active connection."

The Preflight Request (OPTIONS)
For simple requests (like a standard GET), the browser sends the request immediately and blocks the response if the CORS headers are missing.
However, for complex requests—such as a POST, PUT, DELETE, or requests that include custom headers like Authorization or Content-Type: application/json—the browser will pause and send a Preflight Request first.
A preflight request uses the HTTP OPTIONS method. It is the browser's way of asking the server, "I am about to send a DELETE request with an Authorization header from my-app.com. Are you going to allow this?"
The browser will not send the actual, potentially destructive DELETE request until the server replies to the OPTIONS request with explicit approval.

Because CORS is a browser-side enforcement, you cannot fix a CORS error from the frontend code. The backend server must be configured to send the correct headers in its response.

Access-Control-Allow-Origin: [https://my-app.com](https://my-app.com) (Who is allowed to read this).
Access-Control-Allow-Methods: GET, POST, PUT, DELETE (What actions they can take).
Access-Control-Allow-Headers: Content-Type, Authorization (What custom headers they can send).
Note: You can set Access-Control-Allow-Origin: * to allow any domain, but this is highly insecure for APIs requiring authentication and will fail if the frontend tries to send credentials (cookies/tokens).

User prompt: Q12 [Hard]: Walk through the TLS handshake — what happens between a TCP connection being established and the connection being ready to send encrypted HTTPS data? Explain why TLS uses both asymmetric and symmetric encryption instead of picking just one, and describe what role the server's digital certificate plays in preventing a man-in-the-middle attack.
Response: Once the TCP 3-way handshake is complete, the network connection is open, but the data is still in plain text. To secure it, the client and server immediately begin the TLS Handshake.
The goal of this handshake is to agree on how to encrypt the data, verify identities, and securely share a secret key across an unsecure public network.
The TLS Handshake (Step-by-Step)
(Note: This follows the classic TLS 1.2 flow for clarity, though TLS 1.3 optimizes this to fewer steps).
Client Hello: The client sends a message saying, "I want to connect securely. Here is my TLS version, a list of encryption algorithms (cipher suites) I support, and a random string of bytes."
Server Hello & Certificate: The server replies, "Let's use this specific encryption algorithm we both support. Here is my random string of bytes, and here is my Digital Certificate (which contains my Public Key)."
Authentication: The client verifies the server's Digital Certificate against its own OS/browser list of trusted Certificate Authorities (CAs).
Key Exchange (The Pre-Master Secret): The client generates a third random string of bytes (the pre-master secret). It encrypts this string using the server's Public Key and sends it to the server. Because it was encrypted with the public key, only the server's private key can decrypt it.
Session Key Generation: Both the client and the server now have all three random strings. They independently run these strings through a mathematical algorithm to generate the exact same Symmetric Session Key.
Finished: Both sides send a final "Finished" message, encrypted with the new symmetric key, to verify the handshake was successful. All HTTP traffic from this point forward is encrypted.
The Hybrid Strategy: Why use both?
You might wonder why we don't just use one type of encryption for the whole session. The answer is a tradeoff between security and performance.
Asymmetric Encryption (Public/Private Keys): This is mathematically brilliant because it allows two strangers to exchange secrets without ever meeting beforehand to agree on a password. However, the math (like RSA) is incredibly CPU-intensive and slow. If you tried to encrypt a 4K Netflix video stream asymmetrically, your server's CPU would melt, and the video would buffer endlessly.
Symmetric Encryption (One Shared Key): This math (like AES) is incredibly fast and efficient for bulk data. But it has a massive flaw: how do you get the shared key to the client without a hacker stealing it in transit?
The Solution: TLS uses slow, secure asymmetric encryption for just a few milliseconds during the handshake. Its only job is to safely deliver the shared symmetric key. Once both sides have that symmetric key, they abandon the asymmetric keys and use the fast symmetric key to encrypt the actual web traffic.
Defeating Man-in-the-Middle (MITM)
Imagine a hacker sitting at a coffee shop router intercepting your traffic to your fintech trading app (fintech.com).
Without a Digital Certificate, the hacker could intercept your "Client Hello." The hacker replies, "I am fintech.com, here is my public key." You encrypt your pre-master secret with the hacker's public key. The hacker decrypts it, generates the symmetric key, and now can read your passwords in plain text.
The Digital Certificate prevents this. A certificate is issued by a trusted Certificate Authority (like DigiCert or Let's Encrypt). The CA cryptographically signs the server's public key, essentially stamping it to say, "We, the trusted authority, guarantee this public key belongs strictly to fintech.com."
When the hacker tries to send you their fake public key, they cannot forge the CA's mathematical signature. Your browser sees the signature is invalid (or missing), throws a massive red warning screen, and immediately drops the connection before sending any secrets.
The Interview Answer (90 seconds)
*"The TLS handshake happens immediately after the TCP handshake. Its goal is to authenticate the server and securely exchange a symmetric encryption key.
The client sends a 'Hello' with supported ciphers and a random string. The server replies with its chosen cipher, its own random string, and its Digital Certificate containing its public key. The client verifies the certificate, then generates a 'pre-master secret', encrypts it using the server's public key, and sends it over. Now, both sides use those random strings to independently compute the exact same Symmetric Session Key.
TLS uses a hybrid encryption approach for performance. Asymmetric encryption—using public and private keys—is used only during the handshake to securely exchange the secret. Because asymmetric math is computationally expensive and slow, the protocol switches to symmetric encryption for the actual data transfer, which is much faster for bulk data.
Finally, the digital certificate is what prevents Man-in-the-Middle attacks. Without it, a hacker could intercept the handshake and send their own public key. But because the certificate is cryptographically signed by a trusted third-party Certificate Authority, the hacker cannot forge it. The client's browser will instantly recognize the fake key, realize the server is an imposter, and terminate the connection."*

User prompt: Q13 [Easy]: Give a one-line comparison of HTTP/1.1, HTTP/2, and HTTP/3. Specifically: what problem does HTTP/2's multiplexing solve, and why does HTTP/3 switch to QUIC over UDP instead of staying on TCP?
Response: HTTP/1.1 sends requests sequentially over multiple TCP connections; HTTP/2 multiplexes many requests concurrently over a single TCP connection; and HTTP/3 abandons TCP entirely for a new UDP-based protocol (QUIC) to make those multiplexed streams truly independent.
The Problem HTTP/2 Multiplexing Solves
HTTP/1.1 suffers from application-layer Head-of-Line (HoL) blocking. If your browser requests a massive JavaScript file followed by a tiny CSS file on the same connection, the CSS file is stuck waiting in a queue until the JavaScript file completely finishes downloading.
HTTP/2 solves this by introducing multiplexing. It breaks down the HTTP messages into independent, interleaved frames sent over a single TCP connection. The server can send a chunk of the JS file, a chunk of the CSS file, and a chunk of an image all at the exact same time. The browser receives these mixed frames and reassembles them, meaning a slow, heavy request no longer blocks lighter requests behind it.
The Problem HTTP/3 (QUIC) Solves
While HTTP/2 fixed application-layer blocking, it inherited a fatal flaw from TCP: transport-layer Head-of-Line blocking.
Because TCP guarantees perfect, ordered delivery of packets, if just one packet is dropped due to a spotty mobile network, TCP halts the entire connection. It waits for the lost packet to be retransmitted before letting the application process any subsequent packets. Because HTTP/2 jams all of a website's files into a single TCP connection, one dropped packet halts the loading of the entire website.
HTTP/3 solves this by replacing TCP with QUIC, a protocol built on top of UDP. QUIC understands that the multiplexed streams are independent. If a packet belonging to an image drops, QUIC only pauses the stream for that specific image. The rest of the CSS, JavaScript, and HTML continue streaming flawlessly over the UDP connection without waiting.
The Interview Answer (60 seconds)
"To summarize the evolution: HTTP/1.1 processes requests sequentially over TCP. HTTP/2 introduced multiplexing to process requests concurrently over a single TCP connection. HTTP/3 moves away from TCP entirely, using a UDP-based protocol called QUIC.
HTTP/2 introduced multiplexing to solve application-layer Head-of-Line blocking. Instead of a large file holding up the queue for smaller files, HTTP/2 chops them into frames and sends them simultaneously over one connection.
However, because HTTP/2 relies on TCP, it suffers from transport-layer Head-of-Line blocking. If a single packet drops on a spotty network, TCP halts the entire connection waiting for a retransmission, meaning all multiplexed files are paused. HTTP/3 fixes this by switching to QUIC over UDP. QUIC manages streams independently—so if a packet for an image is lost, only that image is delayed, while the rest of the web page continues loading without interruption."

Response: Step-by-Step Breakdown
1. Compute the Checksum (Sender Side) The Internet checksum method involves summing the data segments using one's complement arithmetic and then taking the one's complement of the result.
Data Segment 1: 10101001 (169 in decimal)
Data Segment 2: 00111001 (57 in decimal)
First, add the two segments together:
  1010 1001
+ 0011 1001
-----------
  1110 0010  (226 in decimal)


(Note: If there had been a carry-out bit beyond the 8th bit, we would wrap it around and add it to the least significant bit. Since our sum is 8 bits, no wraparound is needed.)

Sum: 1110 0010
Checksum: 0001 1101

+ 0011 1001 (Segment 2)
-----------
  1110 0010 (Sum of segments)
+ 0001 1101 (Checksum)
-----------
  1111 1111 


The receiver takes the one's complement of this final sum. The one's complement of 1111 1111 is 0000 0000. Since the result is all zeros, the receiver concludes the data is valid and no transmission errors occurred.
3. Limitations: Checksum vs. CRC The Internet checksum is optimized for software processing speed, but it is mathematically weak. Its primary flaw is position blindness and susceptibility to compensating bit flips.

Check 1 (bits 1, 3, 5, 7): 0, 1, 0, 1. Even. → Pass (0)
Check 2 (bits 2, 3, 6, 7): 1, 1, 0, 1. Odd. → Fail (1)
Check 4 (bits 4, 5, 6, 7): 0, 0, 0, 1. Odd. → Fail (1)

"To encode the 4-bit data 1011, we first use the formula 2r≥m+r+1 to determine we need 3 parity bits, making a 7-bit codeword. We place the parity bits at power-of-two positions—1, 2, and 4—and fill the rest with our data bits. Calculating for even parity gives us the final codeword of 0110011.

(b) Determine the minimum window size required to keep the link fully utilized (i.e., the sender never sits idle waiting for an ACK) — this uses the formula N = 1 + 2a. (c) If the actual window size used is only half of what you calculated in (b), what would the resulting link efficiency be, and why? This question is the natural payoff of P8 — it's where "why Stop-and-Wait is inefficient on long fat networks" turns into an actual number, and the 1 + 2a formula is one of the most frequently tested sliding-window numericals in both OAs and GATE-style papers, so it's worth calling that out directly in the answer.
Response: Step-by-Step Breakdown
1. Calculate Transmission Time and Ratio a
Transmission Time (Tt​): BandwidthFrame Size​=5×106 bps1000 bits​=0.0002 seconds (or 0.2 ms).
Propagation Delay (Tp​): 20 ms.
Calculate a: The ratio a represents how many frames can be put on the wire while the first bit travels to the destination.
a=Tt​Tp​​=0.2 ms20 ms​= 100.
2. Determine Minimum Window Size (N) To keep the link 100% utilized, the sender must continuously transmit frames for the entire duration of a Round Trip Time (RTT).
RTT in terms of Tt​: A full round trip consists of transmitting the frame (Tt​) plus the propagation to the receiver (Tp​) plus the propagation back for the ACK (Tp​). Total cycle time = Tt​+2Tp​.
The Formula: N=1+2a.
Calculation: N=1+2(100)= 201.
The sender must maintain a sliding window of exactly 201 frames. By the time it finishes pushing the 201st frame onto the wire, the ACK for the 1st frame will arrive, allowing the window to slide forward without a single millisecond of idle time.
3. Analyze Efficiency with a Halved Window Size
Actual Window Size (W): Half of 201 is roughly 100.
Efficiency Formula: For any window size W that is smaller than 1+2a, the efficiency η is exactly 1+2aW​.
Result: 201100.5​= 50%.
Why? Because the sender pushes exactly half the number of frames required to fill the total cycle time. It transmits continuously for the first half of the round trip, exhausts its window of 100 frames, and is forced to stop. It then sits entirely idle for the remaining 50% of the time waiting for that first ACK to arrive. The pipeline is only ever half-full.
Concise Interview Answer
(Interview Tip: The N=1+2a derivation is one of the most frequently tested concepts in OAs, GATE-style networking papers, and system design interviews, because it perfectly connects the physical limitations of the wire to the software logic of the protocol.)
"First, we find our transmission delay by dividing the 1000-bit frame by the 5 Mbps bandwidth, giving us a Tt​ of 0.2 milliseconds. We then calculate our ratio a, which is propagation delay over transmission delay (20ms/0.2ms), giving us 100.
To achieve 100% link utilization, the sender must continuously pump data into the link for an entire round-trip time. We calculate this using the standard sliding window formula, N=1+2a. Plugging in 100 gives us a minimum window size of 201 frames. This means we need 201 unacknowledged frames in flight to perfectly fill the pipe so that the first ACK arrives right as we finish sending the 201st frame.
If we restrict our window size to half of that—say, 100 frames—our link efficiency drops linearly to exactly 50%. Conceptually, this happens because the sender is only allowed to fill half of the network's bandwidth-delay product. It will transmit at full speed for the first half of the round trip, exhaust its window limit, and then sit completely idle for the second half of the round trip waiting for the first ACK to release the lock."
